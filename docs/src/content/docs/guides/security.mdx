---
title: Security and privacy
description: Understand encryption, relay-visible metadata, invitations, revocation, and platform limits.
---

Sim Bridge is a prototype for owner-operated bridges. Its design protects message content
from the relay, while leaving some routing metadata visible. A build or passing test suite
does not prove the absence of vulnerabilities or guarantee delivery of sensitive credentials.

## Content encryption

Message bodies, phone numbers, SIM details, event timing, and command contents are sealed
on the originating device with AES-256-GCM under a random 256-bit bridge root key. The root
key is generated locally and transferred by QR invitation or recovery code. It is not
generated by or sent separately to the relay.

The cryptographic boundary applies to APNs previews too: the gateway seals the preview,
Apple and the relay carry ciphertext, and the iPhone decrypts locally. Generic fallback
alerts reveal that a Sim Bridge message arrived, but do not contain its SMS body.

## What the relay observes

The relay still sees bridge/device identifiers, gateway capabilities, ciphertext sizes,
source IP addresses, routing targets, and request timing. End-to-end encryption does not
make traffic anonymous. Application state is RAM-only, but host access logs, swap, crash
dumps, and dashboards require independent review and protection.

Carrier networks and the Android gateway necessarily handle the original SMS. On a paired
client, plaintext becomes visible after decryption. Screen captures, clipboard tools,
notification previews, and a compromised device can expose it outside the relay boundary.

## Commands and enrollment

Every sealed command binds its bridge, sender, target gateway, command ID, and issue time.
The gateway checks those values, a five-minute freshness window, and persistent execution
history before acting. This limits replay and cross-gateway routing attacks even when the
relay cannot read the command.

Gateway capability is set at enrollment and cannot be promoted by an ordinary client.
Owner and enrollment authentication are rate limited. Tokens and enrollment verifiers are
hashed in an in-memory SQLite database. Ciphertext queues have five-minute lifetimes and count caps. No application database or log files are written. The Android owner gateway keeps durable membership and revocation policy and restores authorization after restart. Other devices use independent signing keys to resume their existing identities; shared invitation/root keys never prove ownership. Permanent policy changes need the gateway to save them before success. Trust the current gateway ledger and avoid stale authorization backups. Existing installations need an explicit migration. Host allowlisting and the absence
of wildcard CORS help protect the local service; HTTPS remains necessary outside local hosts.

## Invitations and revocation

Treat the QR invitation and 52-character recovery code as secrets. They grant access to
the bridge root key. Closing enrollment limits new device admission; revocation removes a
device's relay access. Neither action rotates a root key that a prior member already held.

Per-device content keys with forward secrecy and simpler invitation/key rotation remain
future work. Replacing the current bridge root key requires re-pairing devices. Do not share
invitations in public issues, screenshots, or support reports.

## Local storage and clipboard

Credentials use iOS/macOS Keychain, Android Keystore-backed secure storage, Windows encrypted
storage, or Linux Secret Service. Linux must have a running/unlocked compatible Secret Service;
the app does not substitute a plaintext fallback.

Automatic code copying defaults off on desktop. macOS clipboard markers are advisory and
ownership-aware cleanup applies only while appropriate. Windows/Linux use the normal clipboard.
Once copied, a secret is available to other apps and clipboard tools on that computer.

See the [privacy information](/docs/legal/privacy/) and
[terms of use](/docs/legal/terms/) for the project's published policies, and
[support](/docs/support/) for reporting guidance. Never include real SMS content,
